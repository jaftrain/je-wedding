## Summary

All seven routes loaded successfully with expected titles, primary headings, eight navigation links, and no broken images. The deterministic site checker completed with zero errors and zero warnings. Browser testing found that an open mobile navigation did not close with Escape; the shared keyboard handler was updated and the behavior passed a fresh-origin browser retest.

The existing client-side password prompt does not restrict access to static GitHub Pages content. It remains a deployment architecture risk, not a client-side defect that can safely be fixed in this repository.

## Findings

### Medium — Mobile navigation did not close with Escape

- **Confidence:** High
- **Route / device:** All routes using the shared navigation at 390 x 844.
- **Evidence:** With the menu open, pressing Escape left `.nav-links.open` present and the menu toggle's `aria-expanded` value set to `true`.
- **Reproduction:**
  1. Open `schedule.html` at a 390 x 844 viewport.
  2. Activate **Toggle navigation**.
  3. Press Escape.
  4. Observe that the navigation remains open.
- **Expected / actual:** Escape should dismiss the open navigation; previously it did not change its open or ARIA state.
- **Impact:** Keyboard users had no conventional keyboard shortcut to dismiss the mobile navigation.
- **Suggested fix:** Handle Escape in the shared keyboard listener and close the navigation when it is open.
- **Code fix:** Applied in [assets/js/main.js](../assets/js/main.js) by closing the shared mobile navigation from the Escape handler while preserving modal close behavior.
- **Retest:** Passed from a fresh local origin: after Escape, `.nav-links.open` was absent and `aria-expanded` was `false`.

### High — Client-side password prompt does not protect published content

- **Confidence:** High
- **Route / device:** All deployed pages and assets.
- **Evidence:** The site is static and the password comparison runs in browser JavaScript after the HTML and assets are served.
- **Expected / actual:** If the content must be private, unauthenticated requests must be denied before static files are served; the current prompt only hides rendered content.
- **Impact:** Anyone able to reach the public deployment can obtain the page source and static assets. Do not put confidential information behind this prompt.
- **Suggested fix:** Put an authenticated hosting or identity layer in front of the static files, or treat all public GitHub Pages content as non-sensitive.
- **Code fix:** Not applied. This requires a hosting and access-policy decision outside the static-site codebase.
- **Retest:** Not applicable until an access-control architecture is selected; confirm direct unauthenticated page and asset requests are denied after migration.

## Recommendations

- Run Lighthouse against a deployed page at desktop and mobile sizes before making image or performance changes; a local browser run is not field Core Web Vitals data.
- Complete contrast, zoom/reflow, reduced-motion, screen-reader, and cross-browser testing before claiming WCAG conformance.
- Verify RSVP and map destinations from a safe production test plan when those integrations are ready.

## Not tested / limitations

- Production deployment, HTTPS configuration, public-site visibility settings, external RSVP and map destinations, and real-world form submission were not tested.
- No Lighthouse, field Core Web Vitals, full screen-reader audit, contrast measurement, or multi-browser/device matrix was run.
- The no-JavaScript fallback was not browser-tested because JavaScript-disabled browser mode was unavailable.
